# Backend persistence contract inventory

- **Status:** P0-A implementation inventory
- **Architecture plan:** `docs/design/backend-crate-architecture-plan.md`, P0.3
- **Inspected revision:** `a75ff73c187e1ae9bae04fd9f1377e8662886242` plus the working tree as of 2026-08-31

- **Coverage:** all 139 operations declared by those ports, including `BootstrapRepository`

## 1. Purpose

This document records what the current code does before the backend is split into core, host, PostgreSQL, and Turso crates. It is an implementation inventory, not a declaration that every current behavior is desirable.

Where both adapters agree and the behavior is visible in callers or tests, this document records it as observed behavior. Where ordering, time bounds, transactions, or outcomes differ, the disagreement is explicitly marked. P2/P3 must resolve each disagreement in an ADR or shared adapter contract test before deleting the corresponding member of the old `Persistence` aggregate.

No semantic choice is made merely because one adapter happens to implement it first.

## 2. Reading conventions

### 2.1 Scope

- **Tenant:** every lookup or mutation is qualified by `TenantId`.
- **Device:** the operation receives a previously resolved `DeviceIdentity` containing tenant and device IDs.
- **System:** the operation intentionally spans tenants or stores process-wide data.
- **Operational:** database lifecycle or engine maintenance, not a core business repository.

The current schema and ingress flow assume protocol device IDs are globally unique. Methods that resolve only a device ID are therefore marked system/device-bootstrap scope even though their result contains a tenant.

### 2.2 Result terminology

- **Empty** means a successful empty collection or zero-valued projection.
- **Not found** means `None`, `false`, or a typed `*NotFound` outcome, as stated in each row.
- **Conflict** means either a typed domain outcome or a `PersistenceError` generated by a database constraint. These are not interchangeable.
- Unless a row says otherwise, duplicate inserts are not specified as idempotent and currently surface a constraint error.

### 2.3 Time

PostgreSQL models frequently expose database timestamps as `NaiveDateTime`; Turso stores UTC epoch microseconds and decodes them through `row::datetime`. Current callers treat all `NaiveDateTime` values as UTC. That convention is implicit and must become an explicit UTC boundary in P1.5/P2.3.

“DB clock” below means the method does not receive a timestamp and obtains one from a database default or `Utc::now()` in the adapter. Supplied `DateTime<Utc>` values are converted to PostgreSQL naive UTC or Turso epoch microseconds. No shared test currently establishes round-trip precision for either adapter.

### 2.4 Evidence labels

- **PG impl / T impl:** the PostgreSQL or Turso adapter source is the evidence; this is not a behavioral test.
- **PG API:** `crates/backend/tests/api_tests.rs`.
- **PG cert:** `crates/backend/tests/cert_tests.rs`.
- **T blueprint:** `persistence::turso::tests::device_blueprint_draft_and_revision_round_trip`.
- **T analytics:** `persistence::turso::tests::analytics_catalogs_and_queries_blueprint_metrics`.
- **T foundation:** `persistence::turso::tests::identity_and_catalog_foundation_round_trip`.
- **Service unit:** a recording/mock repository test verifies authorization, normalization, or tenant propagation but not adapter semantics.

Implementation files are evidence for every row. A row that says “no direct test” means no test was found that asserts the listed persistence behavior across an actual adapter.

## 4. Cross-cutting observations

### 4.1 Tenant enforcement

All tenant-shaped methods inspected include tenant predicates in both adapters. Device-ingress writes use the tenant-qualified `DeviceIdentity`. System methods are nevertheless mixed into business ports: rule-cache loading, retention, legacy blob migration, certificate re-encryption, server metrics, and bootstrap all span tenants.

The current alert-retention worker is a special hazard: `delete_resolved_before` is tenant-scoped, but the worker calls it only for `DEFAULT_TENANT_ID`. This is not a valid multi-tenant retention contract and must be resolved in P3.3.

### 4.2 Error and conflict behavior

PostgreSQL maps named unique, foreign-key, check, and serialization failures. Turso maps constraint categories to generic names (`unique`, `foreign_key`, `check`) and maps most other engine errors to `Internal`. Callers generally match only the category, not the name, but no shared test proves equivalent public errors.

Typed outcomes are already used for important expected states: last-owner protection, in-use deletion, stale blueprint drafts, missing devices, incompatible firmware, and invalid alert transitions. Those outcomes should remain typed core results. Raw constraint errors should not be promoted into new domain outcomes without an explicit P3 decision.

### 4.3 Ordering, pagination, and collation

Repository methods accept already-normalized limits/offsets; validation and caps live in services/HTTP. Most catalog lists use offset pagination and return a separate total. Name ordering uses each engine's default collation, so even matching `ORDER BY name, id` clauses do not prove identical case or Unicode behavior.

Several PostgreSQL lists omit an ID tie-breaker that Turso includes. Rule and analytics-catalog top-level ordering still differs outright. Zone ordering is resolved by ADR-006, role ordering by ADR-007, and user/assigned-role/permission ordering by ADR-008; all three migrated slices are enforced by shared adapter contracts.

### 4.4 Transactions and retries

Methods explicitly documented as atomic generally use a PostgreSQL transaction and a Turso writer transaction. There are important exceptions recorded below: telemetry maintenance, metrics retention, CI firmware ingestion, some read-then-write paths, and host-side object/publication orchestration.

Read methods are retry-safe. Delete methods and compare-and-set updates are normally retry-safe but may return a different boolean/outcome after the first successful call. Creation is generally not idempotent unless it uses `ON CONFLICT DO NOTHING` or a stable event ID. Workers currently implement their own backoff; repository errors do not provide a uniform retry policy.

### 4.5 Current test shape

PostgreSQL coverage is mostly HTTP integration coverage. Turso has three broad adapter round trips. Service unit tests verify security/tenant propagation for only some domains. There is no shared adapter semantic suite, and the broad Turso foundation test does not exercise most negative, concurrency, ordering, boundary-time, or retry cases.

## 7. Shared contract-suite implications

The `backend-adapter-tests` package grows one slice at a time and should use a fresh backend per contract group. The completed zone and role suites plus the structurally complete user suite establish the pattern; the user security additions and remaining suites must cover, at minimum:

1. tenant isolation for every tenant port, including cross-tenant IDs that otherwise exist;
2. typed not-found/in-use/stale outcomes independently from constraint failures;
3. exact ordering with equal timestamps, mixed-case names, and stable ID ties;
4. offset pages at zero, the final partial page, and beyond the final page;
5. exact lower/upper time boundaries and UTC microsecond round trips;
6. duplicate create, repeated delete/update, lost-response retry, and duplicate input IDs;
7. concurrent compare-and-set/last-owner/claim/publish/transition behavior;
8. rollback after each step of device provisioning, event/telemetry action enqueue, firmware metadata, and aggregate child replacement;
9. authoritative command, alert, outbox, rule-cache, metrics, and certificate state machines;
10. adapter capability differences such as PostgreSQL partitions/pool counts and Turso checkpointing without leaking those differences into core ports.

Each P2/P3 slice should copy the relevant rows from this inventory into executable tests. The old `Persistence` member can be removed only when every operation in its coverage-index row is either present on a target port with shared tests or intentionally removed by an approved ADR.
